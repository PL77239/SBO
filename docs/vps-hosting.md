# Hosting SBOL on a public VPS

How the current tree is meant to run when players connect from the internet.

## Architecture

```text
[Game clients]  --TCP 47701-->  [Battle Server]  --TCP 7946-->  [DB / Management Server]
                                     |                              |
                              config.json                    config.json
                              data\rivals\, P.DAT, …         sbol.db (SQLite) or MySQL
                              serverkey.bin  <---------------  generated by DB Server
```

| Process | Role | Default port | Who should reach it |
|---------|------|--------------|---------------------|
| **SBOL DB Server** | Accounts, garage, items, auth for Battle | **7946** | Battle Server only (prefer localhost) |
| DB optional web UI | `webserver` in DB config | **8080** | Admin only — do **not** leave open to the world |
| **SBOL Battle Server** | Gameplay, courses, rivals | **47701** | Players (public) |

Both servers `bind` to `INADDR_ANY` (all interfaces). Clients use `game_client/SERVER.INI` → Battle host/port.

> These are **Windows** Visual Studio builds. Easiest public host: a **Windows Server VPS**. Linux is possible only via Wine or a future native port — not the documented path.

---

## 1. VPS prep (Windows)

1. Windows Server (or Windows 10/11 VPS) with a **public IPv4**.
2. Install VC++ runtime if the exes complain (matching your toolset, e.g. VS 2022).
3. Copy onto the VPS (example layout):

```text
C:\SBOL\
  DB\          ← built "SBOL DB Server" + config.json + csp_crypt.dll + libs
  Battle\      ← built "SBOL Battle Server" + config.json + data\ + serverkey.bin + libs
```

Build **Release|Win32** (or Debug) on a Windows box, then copy the output folders + `data\` from the Battle project.

---

## 2. Configure DB Server

Edit `DB\config.json` (from `DB_Server/SBOL DB Server/config.json`):

```json
{
  "databasetype": "sqlite",
  "databasename": "sbol.db",
  "databasehost": "localhost",
  "databaseusername": "sbol",
  "databasepassword": "sbol",
  "databaseport": 3306,
  "serverport": 7946,
  "webserver": false,
  "webserverport": 8080,
  "logpath": ".\\log"
}
```

Recommendations for a first public host:

- Keep **`sqlite`** until you need multi-Battle or heavier load; then MySQL.
- Set **`webserver": false`** unless you firewall **8080** tightly.
- First run creates/opens `sbol.db` and related tables if missing.

Start **SBOL DB Server.exe** first. Confirm it logs listening on **7946**.

Copy the generated **`serverkey.bin`** into the Battle Server folder (Battle expects it next to the exe; local tree also has one under the Battle project).

---

## 3. Configure Battle Server

Edit `Battle\config.json`:

```json
{
  "servername": "SBOL Public",
  "serverport": 47701,
  "serverclientlimit": 100,
  "serverwelcomemessage": "Welcome",
  "managementserverport": 7946,
  "managementserveraddress": "127.0.0.1",
  "logpath": ".\\log"
}
```

- On a **single VPS**, keep `managementserveraddress` as **`127.0.0.1`** / `localhost` so **7946 is not exposed**.
- Ensure `Battle\data\` is present (rivals JSON, etc.) — post-build robocopy normally copies `data` into `OutDir`.

Start **SBOL Battle Server.exe** after DB is up. Confirm it connects to management and listens on **47701**.

---

## 4. Firewall

**Inbound (public):**

| Port | Proto | Allow |
|------|-------|--------|
| **47701** | TCP | Players → Battle |

**Do not publish (or restrict to your IP):**

| Port | Why |
|------|-----|
| **7946** | DB/management — Battle should use loopback |
| **8080** | DB web UI if enabled |
| RDP **3389** | Harden / VPN / allowlist |

Windows Firewall example (admin PowerShell):

```powershell
New-NetFirewallRule -DisplayName "SBOL Battle" -Direction Inbound -Protocol TCP -LocalPort 47701 -Action Allow
```

Cloud panel (AWS SG, Azure NSG, Hetzner, etc.): open **TCP 47701** only for game traffic.

---

## 5. Point clients at the VPS

On each player PC, `game_client/SERVER.INI` (or the folder they launch):

```ini
[SERVER1]
TYPE=0
ADDR=YOUR.VPS.PUBLIC.IP
PORT=47701
SIDE=0

[SERVER2]
TYPE=0
ADDR=YOUR.VPS.PUBLIC.IP
PORT=47701
SIDE=0
```

Use the same values in both slots for a single Battle instance.  
`TYPE=0` / `SIDE=0` matches the usual local working setup.

Optional: DNS name (e.g. `sbol.example.com`) instead of raw IP if you have one.

Players still need the game client + dgVoodoo as usual; only `SERVER.INI` changes for multiplayer host.

---

## 6. Boot order & keep-alive

1. Start **DB Server**  
2. Start **Battle Server**  
3. Clients connect  

For unattended VPS:

- Task Scheduler “At startup” for both exes, **or**
- NSSM / WinSW as Windows services  

If Battle starts before DB is listening, restart Battle after DB is up.

---

## 7. Split hosts (optional)

| Box A (DB) | Box B (Battle) |
|------------|----------------|
| DB Server on 7946 | Battle: `managementserveraddress` = Box A private IP |
| Firewall: **7946 only from Box B** | Public **47701** |

Prefer private networking between A and B; never leave 7946 open to `0.0.0.0/0`.

---

## 8. Checklist

- [ ] DB running, `sbol.db` OK  
- [ ] `serverkey.bin` in Battle folder  
- [ ] Battle connects to management (`127.0.0.1:7946`)  
- [ ] TCP **47701** open on VPS + cloud firewall  
- [ ] **7946** / **8080** not public  
- [ ] Client `SERVER.INI` → VPS IP / DNS + `47701`  
- [ ] Test login + join Main from a machine outside the VPS  

---

## 9. Limits / gotchas

- **Windows binaries** — plan a Windows VPS unless you maintain Wine yourself.  
- **One Battle** on 47701 in the simple layout; scale later with more Battle processes + management routing if the project supports it.  
- Launcher may still reference old patch URLs (`patch.sb-online.net`); for a private host, launch **`SBClient.exe`** with a correct `SERVER.INI` rather than relying on the stock patcher.  
- Back up `sbol.db` regularly.  
- Admin chat / `!` commands: treat public servers as hostile — lock privileges in DB for normal accounts.

When you move from LAN `127.0.0.1` to public, the only required client change is **`SERVER.INI` ADDR**; server-side, bind is already all-interfaces — firewall and “DB on localhost” are the important parts.
